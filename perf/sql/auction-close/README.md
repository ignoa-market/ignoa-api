# 경매 자동 마감 측정

## 시나리오

경매 1,500건을 한꺼번에 만료시키고, 자동 마감 Job이 얼마나 빨리 정확하게 처리하는지 본다.

| 시나리오 | 조건 | 비교 대상 |
|---|---|---|
| 마감 단독 | 1,500건 동시 만료, 다른 요청 없음 | 기존 결과 (4회 평균): 전체 처리 4.60초, 최대 지연 5.64초 |
| 마감 + 부하 | 위 조건 + `browse-bid` (조회 약 200 RPS + 입찰 50 RPS) | 마감 단독, `browse-bid` 단독 |

- 상품마다 입찰 10건이 있어서, 마감되면 낙찰 1건, 패찰 9건, 채팅방, 결제 대기 거래가 생긴다.
- 목표: 모든 경매가 10초 안에 마감, 불일치 0건

## 실행

운영 DB에서 실행한다. 아래가 한 회차다.

1. `1-seed.sql`: 경매 1,500건 생성 (종료 시각은 하루 뒤)
2. *(마감 + 부하만)* `./perf/k6/run.sh browse-bid once` 시작 → 약 2분 대기
3. `2-expire.sql`: 종료 시각을 지금으로 바꿈 → **측정 시작**. `expire_started_at` 기록
4. 대기: 밀린 경매 수가 0이 될 때까지 (Grafana `ignoa-api / 경매 마감`). 마감 + 부하는 k6가 끝날 때까지
5. `3-verify.sql`: `invalid_items = 0` 확인
6. `4-cleanup.sql`: `remaining_* = 0` 확인. 마감 + 부하는 `perf/k6/cleanup.sql`도

## 기록할 값

| 어디서 | 값 |
|---|---|
| `3-verify.sql` | 마감 지연 p50, p95, p99, 최대 / 10초 안에 끝난 비율 / 첫 마감 ~ 마지막 마감 시간 |
| Grafana | 마감 지연 p50, p99 / 밀린 경매 수 최대 / Job 실행 시간 / HikariCP Active, Pending / CPU |

## 특이사항

- **이전 회차 데이터**: 측정 데이터 이름이 `PERF`로 고정이라, 정리를 안 하면 다음 회차 결과에 섞인다. 6번의 0 확인을 건너뛰지 않는다.
- **워밍업**: 배포 직후 첫 회차는 결과에서 뺀다.
- **결제 기한**: 마감으로 생긴 거래는 24시간 뒤 결제 기한이 지난다. 그 전에 정리한다.
- **지연 교차 확인**: DB 기준 지연(종료 시각 → 거래 생성 시각)과 Grafana 지연은 거의 같아야 한다. 크게 다르면 지표 기록을 의심한다.
