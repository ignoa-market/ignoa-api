# 모니터링 가이드

운영 서비스(ignoa-api, ignoa-payment)를 어떤 화면과 알림으로 지켜보는지 정리한 문서

이 폴더의 JSON·YAML은 Grafana Cloud(`ignoa.grafana.net`)에 적용된 설정의 기록이다.

## 무엇이 있나

### 수집 경로

| 신호 | 수집 | 저장 |
|---|---|---|
| 지표 | Alloy가 60초마다 `/actuator/prometheus` 수집 | Mimir |
| 트레이스 | OTel agent → Alloy (모니터링 요청은 샘플링에서 제외) | Tempo |
| 로그 | Alloy가 Docker 컨테이너 로그 수집 | Loki |
| 에러 | 앱의 `ERROR` 로그를 Sentry가 직접 수집, OTel `trace_id`를 태그로 붙임 | Sentry |

### 대시보드

| 대시보드 | 답하는 질문 | 주요 내용 |
|---|---|---|
| `ignoa / 개요` | 서비스가 정상인가? | api·payment 수집 상태(UP/DOWN), 요청 수, 5xx 비율, 응답 시간(p99·평균) |
| `ignoa-api / 자원` | 무엇이 부족한가? | CPU·Heap·GC, DB 커넥션, Tomcat 스레드, 분산 락 |

자원 대시보드 상단 카드는 위험 수준에 따라 색이 바뀐다.

| 카드 | 주황 | 빨강 |
|---|---|---|
| Heap 사용률 | 70% 이상 | 85% 이상 |
| Tomcat 스레드 사용률 | 50% 이상 | 80% 이상 |
| HikariCP 대기 | — | 1건 이상 |

### 알림 (Slack `#ignoa-alert`)

| 알림 | 언제 오나 | 심각도 |
|---|---|---|
| `TargetDown` | 서버 지표가 수집되지 않음 (앱 중단은 약 3분, EC2 전체 중단은 약 4~5분 뒤 알림) | critical |
| `HighErrorRate` | 5xx 비율이 5분 이상 5% 초과 | warning |

두 알림 모두 1분마다 평가하고, 서버별로 따로 보낸다. 장애가 이어지면 4시간마다 다시 알리고, 회복된 상태가 2분 이어지면 `RESOLVED`를 보낸다.

| 설정 | `TargetDown` | `HighErrorRate` |
|---|---|---|
| 알림까지 지속 시간 (Pending) | 2분 | 5분 |
| 쿼리 결과가 없을 때 | 알림 | 정상 |
| 쿼리 자체가 실패할 때 | 알림 | 직전 상태 유지 |

## 왜 이 기준인가

- `TargetDown`은 서버가 통째로 멈춰 지표가 사라진 경우도 장애로 본다. 서버가 멈추면 Alloy도 함께 멈춰 값이 0이 아니라 아예 없어지기 때문이다.
- 지표 저장소는 새 값이 없어도 마지막 값을 5분간 보여준다. 그대로 두면 EC2가 멈춘 뒤 알림까지 약 7분이 걸려서, 최근 2분 안에 값이 없으면 사라진 것으로 판단한다. 2분은 60초 수집이 한 번 늦어도 오탐이 나지 않는 범위다.
- `HighErrorRate`는 최근 5분 요청이 10건 미만이면 판단하지 않는다. 요청 1건 중 1건 실패를 100%로 보는 오탐을 막기 위해서다.
- `HighErrorRate`는 쿼리 실패 시 알리지 않는다. 같은 상황을 `TargetDown`이 이미 알리므로 중복을 피한다.
- 알림은 서버별로 따로 온다. 한 서버의 알림이 다른 서버 알림에 묶여 늦게 오지 않게 하기 위해서다.

## 알림이 오면

1. 개요 대시보드에서 어느 서버의 어떤 지표가 이상한지 확인한다.
2. 자원 대시보드에서 부족한 자원을 확인한다.
3. 에러라면 Sentry 이벤트의 `trace_id` 태그로 Tempo(요청 흐름)와 Loki(앞뒤 로그)를 조회한다.
