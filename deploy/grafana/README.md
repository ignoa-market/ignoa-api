# 모니터링 가이드

운영 서비스(ignoa-api, ignoa-payment)를 어떤 화면과 알림으로 지켜보는지 정리한 문서

이 폴더의 JSON·YAML은 Grafana Cloud(`ignoa.grafana.net`)용 설정이다. 파일 변경만으로 Cloud에 반영되지 않으므로, 변경한 대시보드 JSON은 같은 UID의 대시보드에 덮어쓰기 적용이 필요하다.

## 무엇이 있나

### 수집 경로

| 신호 | 수집 | 저장 |
|---|---|---|
| 지표 | Alloy가 60초마다 `/actuator/prometheus` 수집 | Mimir |
| 트레이스 | OTel agent → Alloy (모니터링 요청은 샘플링에서 제외) | Tempo |
| 로그 | Alloy가 Docker 컨테이너 로그 수집 | Loki |
| 에러 | 앱의 `ERROR` 로그를 Sentry가 직접 수집, OTel `trace_id`를 태그로 붙임 | Sentry |

### 대시보드

| 대시보드 | 답하는 질문 | 주요 내용 |
|---|---|---|
| `ignoa / 개요` | 서비스가 정상인가? | api·payment 수집 상태(UP/DOWN), 응답별 요청 수(2xx·4xx·5xx), 5xx 비율, 응답 시간(p50·p95·p99) |
| `ignoa-api / 자원` | 무엇이 부족한가? | CPU·Heap·GC, DB 커넥션 상태·획득 시간·timeout, Tomcat·JVM 스레드 |
| `ignoa-api / 경매` | 입찰·상품 처리가 정상이고 제때 마감되는가? | 입찰 결과·조회/입찰/수정 응답 시간, 마감 지연·1건/배치 처리 시간·밀린 경매 수·결과별 마감 건수, 상품 기능별 요청량·5xx (11개 패널) |
| `ignoa / 결제·거래` | 결제 준비·승인 요청이 느리거나 오류가 발생하는가? | 결제 API 요청량·HTTP 오류, 준비·승인 API p50·p95·p99 (3개 패널) |

통합 경매 화면은 기존 마감 대시보드 UID(`ignoa-api-auction-close`)와 밀린 경매 수 패널 ID(`3`)를 유지해 알림 링크를 보존한다. 이전 상품 경매 주소(`ignoa-api-bid`)는 통합 화면으로 이동하는 안내만 표시한다.

경매 대시보드의 마감 지연은 경매 1건마다 종료 시각부터 서버에서 낙찰이 확정되기까지의 시간이고(사용자 화면 반영은 미포함), 배치 1회 처리 시간은 한 번에 처리한 건수(최대 1,000건)에 따라 달라지므로 초당 마감 건수와 함께 본다.

경매 대시보드에서 API별 요청 수는 HTTP 지표로, 반영·조건 불충족은 `bid_place_total`로 확인한다. 후자는 `accepted`와 `price_conflict`만 집계하므로 인증 실패나 서버 오류를 포함한 전체 요청 수와 다를 수 있다. `price_conflict`는 가격뿐 아니라 상품 상태·마감 조건 불충족도 포함한다.

수정에 사용하는 DB 비관적 락의 대기·보유 시간은 현재 별도로 수집하지 않는다. 수정 응답 시간에는 파일 업로드와 검증도 포함되며, HikariCP 획득 시간은 DB 커넥션을 빌리기까지의 시간이다. 둘 다 DB 행 잠금 대기 시간 자체로 해석하지 않는다. 수정·입찰 동시 부하에서는 경매 대시보드의 API별 응답 시간·5xx와 자원 대시보드의 커넥션 pending·timeout을 함께 보고, 행 잠금 원인 확인이 필요하면 DB 지표·트레이스·로그를 추가로 확인한다.

저장소의 Alloy 기본 수집 간격은 60초다. 부하 테스트에서 서버 설정을 15초로 바꿨다면 Grafana 데이터 소스의 수집 간격 설정도 실제 값과 맞춰 `$__rate_interval`을 사용한다. 수집 사이의 순간적인 pending 최댓값은 누락될 수 있다. 테스트 전에는 개요 대시보드의 수집 상태와 배포 시각도 확인한다.

### 결제·거래 대시보드 적용

`dashboards/ignoa-payment-trade.json`을 Grafana의 Dashboards → New → Import에서 가져온다. UID는 `ignoa-payment-trade`이며 Prometheus 데이터 소스 UID는 기존과 같은 `eg0q0rxkuivwgc`다. 다른 Grafana 환경이라면 데이터 소스 UID를 맞춘다. 개요·자원·경매 화면에도 이동 링크를 추가했다.

패널은 결제 API 요청량·HTTP 오류, 준비 API p50·p95·p99, 승인 API p50·p95·p99의 3개다. HTTP 패널은 기존 `http.server.requests` 히스토그램을 사용한다. HTTP 200도 결제 성공을 보장하지 않으며, UNKNOWN 이후의 콜백·복구 대기는 API 응답 시간에 포함되지 않는다. 트래픽이 적은 시간의 p99는 요청량과 함께 해석한다.

메인 서버와 결제 서버의 구현·설정 변경 없이 기존 HTTP 지표를 사용한다. 대시보드 전용 DB 조회나 지표 계측 코드는 추가하지 않는다.

JSON만으로 Grafana Cloud에 자동 적용되지 않는다. 로컬 검증은 `python3 deploy/grafana/tests/validate-payment-dashboard.py`로 실행하며 Docker와 `prom/prometheus:v3.12.0` 이미지를 사용한다. 패널 배치와 PromQL 문법을 확인한다. Cloud의 실제 렌더링과 운영 지표 노출은 별도로 확인한다.

### 자원 패널 임계값

자원 대시보드 상단 카드는 위험 수준에 따라 색이 바뀐다.

| 카드 | 주황 | 빨강 |
|---|---|---|
| Heap 사용률 | 70% 이상 | 85% 이상 |
| Tomcat 스레드 사용률 | 50% 이상 | 80% 이상 |
| HikariCP 대기 | — | 1건 이상 |

### 알림 (Slack `#ignoa-alert`)

| 알림 | 언제 오나 | 심각도 |
|---|---|---|
| `TargetDown` | 서버 지표가 수집되지 않음 (앱 중단은 약 3분, EC2 전체 중단은 약 4~5분 뒤 알림) | critical |
| `HighErrorRate` | 5xx 비율이 5분 이상 5% 초과 | warning |
| `AuctionCloseBacklog` | 밀린 경매가 1분 이상 20건 초과 (경매 대시보드의 밀린 경매 수 패널과 연결) | warning |

모든 알림은 1분마다 평가하고, `TargetDown`·`HighErrorRate`는 서버별로 따로 보낸다. 장애가 이어지면 4시간마다 다시 알리고, 회복된 상태가 2분 이어지면 `RESOLVED`를 보낸다.

| 설정 | `TargetDown` | `HighErrorRate` | `AuctionCloseBacklog` |
|---|---|---|---|
| 알림까지 지속 시간 (Pending) | 2분 | 5분 | 1분 |
| 쿼리 결과가 없을 때 | 알림 | 정상 | 정상 |
| 쿼리 자체가 실패할 때 | 알림 | 직전 상태 유지 | 직전 상태 유지 |

## 왜 이 기준인가

- `TargetDown`은 서버가 통째로 멈춰 지표가 사라진 경우도 장애로 본다. 서버가 멈추면 Alloy도 함께 멈춰 값이 0이 아니라 아예 없어지기 때문이다.
- 지표 저장소는 새 값이 없어도 마지막 값을 5분간 보여준다. 그대로 두면 EC2가 멈춘 뒤 알림까지 약 7분이 걸려서, 최근 2분 안에 값이 없으면 사라진 것으로 판단한다. 2분은 60초 수집이 한 번 늦어도 오탐이 나지 않는 범위다.
- `HighErrorRate`는 최근 5분 요청이 10건 미만이면 판단하지 않는다. 요청 1건 중 1건 실패를 100%로 보는 오탐을 막기 위해서다.
- `HighErrorRate`는 쿼리 실패 시 알리지 않는다. 같은 상황을 `TargetDown`이 이미 알리므로 중복을 피한다.
- 알림은 서버별로 따로 온다. 한 서버의 알림이 다른 서버 알림에 묶여 늦게 오지 않게 하기 위해서다.
- `AuctionCloseBacklog`는 마감 지연이 아니라 밀린 경매 수를 본다. 마감이 완전히 멈추면 마감 지연은 기록되지 않아 값이 사라지지만, 밀린 경매 수는 계속 늘어나기 때문이다.
- 20건은 평소 처리 속도(초당 약 255건)로 1초 안에 끝나는 양이다. 경매가 고르게 끝날 때도 2~4건이 보이므로 0건 기준은 오탐이 나고, 한꺼번에 1,500건이 끝나도 몇 초 안에 해소되므로 1분 지속 조건(60초 수집 기준 연속 2번)에 걸리지 않는다.
- 지속 시간을 처음에는 3분으로 두었으나, Redis 응답 없음 장애를 재현했을 때 1,500건 마감이 약 1.9분 만에 끝나 알림이 오지 않았다. 정상 몰림은 1분 조건으로도 걸러지므로 1분으로 줄였다.
- `AuctionCloseBacklog`는 지표가 없을 때 알리지 않는다. 앱이 멈춘 상황은 `TargetDown`이 이미 알린다.

## 알림이 오면

1. 개요 대시보드에서 어느 서버의 어떤 지표가 이상한지 확인한다.
2. 자원 대시보드에서 부족한 자원을 확인한다.
3. 에러라면 Sentry 이벤트의 `trace_id` 태그로 Tempo(요청 흐름)와 Loki(앞뒤 로그)를 조회한다.
